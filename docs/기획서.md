# 마티니 동아리 통합 운영 시스템 기획서

> 버전: 0.1 · 작성일: 2026-09-08 · 상태: 검토용 초안
>
> 목적: 동아리 운영 방식과 서비스 화면을 먼저 합의하기 위한 문서이다. 이 문서 작성은 실제 개발·배포·운영 정책 확정을 의미하지 않는다.
>
> 작성 기준: 약 100명의 부원이 있으며, 활동과 운영 방식은 아직 정해지지 않았다는 상황에서 출발한다. 아래의 수치·일정·직책·운영 정책은 별도 표시가 없으면 제안이다.

## 0. 이 문서를 읽고 수정하는 방법

### 0.1 확정된 요구와 제안을 구분한다

| 표시 | 의미 |
|---|---|
| **[요구]** | 사용자가 이번 대화에서 명시한 내용 |
| **[기본안]** | 검토를 위해 임의로 정한 운영·설계 제안. 채택 여부는 미확정 |
| **[결정 필요 D-번호]** | 사용자가 선택하거나 임원들과 합의해야 하는 사안. 21장의 결정표와 연결 |
| **[확장]** | 초기 운영에는 넣지 않고 필요성이 확인되면 추가할 기능 |

**[요구]**

- 동아리 이름은 마티니이며 칵테일 동아리이다.
- 현재 부원은 약 100명이다. 정확한 활동 인원·회비 납부 인원·임원 수는 미확인이다.
- 소개 홈페이지, 행사 참여 신청, 술 재고 관리, 인원 관리가 필요하다.
- 교육, 여러 이벤트, 개강총회 등이 가능한 활동 후보이다. 실제 실시 여부는 미정이다.
- 모바일에서 편리해야 한다.
- 도메인 하나와 웹앱 하나 안에서 소개·부원·임원 공간을 나누는 방향을 검토했다.
- 기존 구현에 얽매이지 않고 운영 전반을 새로 기획한다.
- 지금은 기획서만 작성하며 화면 기획과 미결정 사안을 포함한다.

### 0.2 검토 순서

1. **1~3장:** 어떤 동아리로 운영할지와 실제 가능한 활동을 고른다.
2. **4~10장:** 부원·행사·회비·재고의 기본 운영 규칙을 고른다.
3. **11~14장:** 메뉴와 화면을 확인한다.
4. **18~19장:** 첫 버전 범위와 완료 기준을 확인한다.
5. **21장:** 결정표의 마지막 열을 직접 채운다.
6. **22장:** 실제 자료와 담당자를 준비한다.

각 항목에 찬성·수정·보류를 남겨도 된다. 모든 확장 기능을 결정한 뒤 개발할 필요는 없으며, 21장의 **착수 전 필수** 항목부터 정한다.

### 0.3 기획의 핵심

**마티니를 알아보고, 활동에 참여하고, 운영 기록을 다음 임원에게 넘길 수 있는 하나의 시스템을 만든다.**

- 공개 홈페이지: 동아리가 어떤 곳인지 알려준다.
- 부원 라운지: 다음 활동과 내 신청 상태를 빠르게 확인한다.
- 임원 운영실: 행사 준비부터 출석·정산·재고 정리까지 이어서 처리한다.
- 데이터는 공통으로 관리하되 열람·수정 범위는 역할과 담당 업무에 따라 제한한다.
- 활동이 미정이므로 교육·총회 등을 별개의 프로그램으로 고정 개발하지 않고 공통 행사 틀과 유형별 설정으로 운영한다.

## 1. 목표와 성공 기준

### 1.1 해결할 문제

| 예상 문제 | 시스템에서 해결할 방식 |
|---|---|
| 부원 100명이 누구인지, 누가 이번 학기에 활동하는지 불명확 | 사람과 학기별 활동 상태를 분리한 명부 |
| 신청 정보가 채팅과 여러 폼에 흩어짐 | 행사별 신청 내역과 명단 통합 |
| 입금 확인·취소·환불이 대화에 묻힘 | 신청과 연결된 납부·환불 상태 |
| 술이 얼마나 남았고 누가 사용했는지 모름 | 보관 위치별 재고와 입출고 기록 |
| 행사 담당자가 바뀌면 준비 과정을 다시 만듦 | 행사 템플릿·체크리스트·결과 기록 |
| 모바일에서 넓은 관리 표를 조작하기 어려움 | 현장 작업 전용 모바일 화면 |
| 다음 기수 임원이 이전 운영을 파악하기 어려움 | 학기별 기록, 역할 인수인계, 내보내기 |

이는 현재 확인된 장애 목록이 아니라 설계에서 예방하려는 문제 가설이다.

### 1.2 첫 학기의 검증 목표 [기본안]

- 부원 100명의 명부를 중복 없이 정리하고 학기별 상태를 확인할 수 있다.
- 로그인과 부원 승인이 끝난 사용자는 일반 행사 신청을 약 1분 안에 완료한다.
- 한 행사에서 신청 → 납부 확인 → 출석 → 정산 → 재고 정리까지 연결한다.
- 마지막 한 자리 동시 신청에도 정원 초과 확정과 중복 신청이 발생하지 않는다.
- 임원은 모바일에서 한 사람의 출석이나 한 품목의 사용을 약 30초 안에 기록한다.
- 신규 임원이 이 문서와 운영실 기록으로 다음 행사를 준비할 수 있다.

시간 목표는 사용성 검증을 위한 가설이다. 실제 부원 5명과 임원 2명으로 시험한 뒤 조정한다. 분석을 위해 개인의 모든 클릭을 수집할 필요는 없다.

### 1.3 초기에는 목표로 삼지 않는 것

- 설치가 필수인 iOS·Android 네이티브 앱
- 자체 채팅·SNS·게시판 전체 구축
- 자동 은행 거래 조회와 온라인 결제·송금
- 정식 회계 프로그램 수준의 장부
- 주류 판매·외부 상거래 기능
- 정교한 추천 알고리즘과 음주량 순위
- 운영자가 관리할 수 없는 복잡한 자동화

## 2. 동아리 운영 모델 제안

### 2.1 동아리의 방향 [기본안]

소개 문구 후보:

> 칵테일을 배우고, 함께 만들고, 취향을 나누는 동아리 마티니.

운영의 세 축을 **배움 / 교류 / 기록**으로 둔다.

- 배움: 도구 사용, 재료 이해, 기본 기법, 레시피 실습.
- 교류: 정기 모임, 개강·종강총회, 테마 행사, 팀 활동.
- 기록: 레시피, 활동 후기, 운영 노하우, 재고·예산 이력.

술을 마시는 것만이 참여 방식이 되지 않도록 논알코올 실습, 제작·기록·진행 역할도 마련한다. 실제 주류 제공 대상, 장소 이용 조건, 학교 규정은 운영 전에 확인한다. 법적 자격이나 학교 허가가 확보되었다고 가정하지 않는다. **[결정 필요 D-01, D-04]**

### 2.2 활동 후보

| 활동 | 목적 | 예시 운영 형태 | 필요한 시스템 기능 | 제안 순서 |
|---|---|---|---|---|
| 개강총회·OT | 활동 안내, 신규·기존 부원 교류 | 전체 대상, 참석 여부 조사 | 신청·출석·자료·질문 수집 | 첫 운영 |
| 칵테일 입문 교육 | 초보자의 기본 경험 확보 | 소규모 실습 회차 | 정원·납부·레시피·재료 준비 | 첫 운영 |
| 테마 칵테일 모임 | 다양한 재료와 취향 경험 | 주제별 단회 행사 | 신청·준비물·재고·후기 | 운영 안정 후 |
| 논알코올 워크숍 | 다양한 참여 방식 제공 | 음료 제작 실습 | 일반 행사와 같은 기능 | 초기 후보 |

| 게스트 세미나 | 외부 경험 공유 | 강연·시연 | 참가 신청·질문·예산 | 확장 |
| 견학·외부 방문 | 현장 경험 | 장소·이동 안내 포함 | 신청·참가비·변경 공지 | 확장 |
| 창작 칵테일 발표회 | 학기 성과 공유 | 팀별 제작과 발표 | 팀 신청·레시피·평가 | 확장 |
| 축제·외부 행사 | 공동 프로젝트 | 준비·운영·정리 인력 편성 | 근무표·예산·재고·담당자 | 별도 타당성 검토 |
| 종강총회 | 결산·회고·인수인계 | 활동 결과와 차기 계획 공유 | 참석·집계·자료 | 첫 학기 말 |

행사 이름이 같아도 매 학기에 개최할 의무는 없다. 초기에는 총회 1회와 소규모 교육 1회를 실제로 운영해 보고 반복 규모를 정한다.

### 2.3 한 학기 운영 예시 [기본안]

| 시점 | 운영 업무 | 활동 예시 |
|---|---|---|
| 개강 전 | 기존 명부 정리, 임원 역할 배정, 재고 실사 | 수요 조사 |
| 1~2주차 | 활동 신청·회비 확인, 첫 행사 공지 | 개강총회·OT |
| 3~6주차 | 교육 회차 운영, 취소·대기 규칙 검증 | 입문 교육 2~3회 |
| 중간고사 전후 | 활동 빈도 조정, 재고 점검 | 휴식 또는 소규모 모임 |
| 9~13주차 | 선호도에 맞춰 활동 추가 | 테마 모임·워크숍 |
| 학기 말 | 정산, 재고 실사, 활동 회고 | 종강총회 |
| 방학 전 | 차기 임원 인수인계, 보존 자료 정리 | 다음 학기 계획 |

위 주차는 실제 학사 일정이 아니다. **[결정 필요 D-02, D-03]**

### 2.4 100명 규모를 운영하는 방식

- 전체 부원을 특정 교육 한 회차에 모두 수용한다고 가정하지 않는다.
- 교육 정원은 장소·도구·진행자 수를 확인한 뒤 정한다. 예시 정원 20명은 테스트용 수치이다.
- 같은 교육을 회차별로 반복하고, 다른 회차와의 중복 신청 제한은 실제 필요 시 추가한다.
- 첫 학기는 선착순을 기본안으로 두되 반복 참여 편중이 생기면 신규 참여자 우선 또는 추첨을 검토한다.
- 추첨을 도입한다면 대상·일정·취소 규칙·결과 기록을 별도 정의한다.
- 부원 100명이라는 명부 수와 행사별 참석 인원은 별개로 집계한다.

## 3. 조직과 담당 업무

### 3.1 역할 제안

직책을 반드시 이대로 만들 필요는 없다. 소수 임원이 여러 역할을 맡을 수 있으며, 직책명과 시스템 권한은 분리한다.

| 역할 | 주 업무 | 시스템 권한 기본안 |
|---|---|---|
| 운영 책임자 | 정책·학기 운영·인수인계 | 주요 설정, 담당자 지정 |
| 부원 담당 | 가입 승인, 명부·활동 상태 | 부원 관리 |
| 행사 담당 | 일정·모집·참가자·현장 운영 | 지정 행사 관리 |
| 교육 담당 | 교육 내용·레시피·자료 | 지정 교육·자료 관리 |
| 재무 담당 | 회비·참가비·지출·환불 확인 | 재무 관리 |
| 재고 담당 | 입고·사용·실사·발주 제안 | 재고 관리 |
| 홍보 담당 | 소개·모집·활동 사진 | 공개 콘텐츠 관리 |
| 현장 도우미 | 특정 행사 출석·준비 | 해당 행사에 한정한 임시 권한 |

### 3.2 운영 업무와 시스템 권한 원칙 [기본안]

- 로그인했다고 바로 부원 또는 임원이 되지 않는다.
- 부원 승인과 임원 권한 부여는 서로 다른 업무이다.
- 재고 담당자에게 전체 부원의 연락처나 회계 증빙을 자동 공개하지 않는다.
- 행사 담당자는 담당 행사 참가자의 필요한 정보만 본다.
- 임원 임기와 담당 범위를 저장하고, 인수인계 시 회수 여부를 확인한다.
- 임원 권한 부여·회수·중요 설정 변경 이력을 남긴다.
- 공용 비밀번호를 공유하는 운영 방식은 채택하지 않는다.
- 최초 운영 책임자 지정과 계정 복구 절차는 출시 전 결정한다. **[결정 필요 D-05, D-06]**

## 4. 서비스 구조와 로그인

### 4.1 기본 구조 [기본안]

- 도메인 1개, 웹앱 1개, 공통 인증과 데이터 저장소를 사용한다.
- 공개·부원·임원 공간은 서로 다른 메뉴와 화면 구성을 가진다.
- 데이터베이스 하나라는 말은 모든 정보를 모든 사용자에게 공개한다는 뜻이 아니다.
- 화면 주소, 서비스 이름, 도메인은 아래 예시를 바탕으로 최종 결정한다.
- 개발·검증 환경과 실제 부원 데이터가 있는 운영 환경은 구분한다.

~~~mermaid
flowchart TB
    V[일반 방문자] --> P[공개 홈페이지]
    M[승인된 부원] --> L[부원 라운지]
    O[담당 임원] --> A[임원 운영실]
    P --> PUB[공개용 정보]
    L --> ACCESS[인증·권한 검사]
    A --> ACCESS
    ACCESS --> DATA[부원·행사·신청·재무·재고]
    DATA --> PUB
~~~

공개용 정보에는 동아리 소개, 공개 행사 요약, 허가된 사진만 포함한다. 원본 명부와 신청서를 그대로 공개하지 않는다.

### 4.2 계정과 부원 연결

1. 사용자가 선택된 로그인 방식으로 로그인한다.
2. 기존 부원은 명부 연결 요청을 한다.
3. 시스템은 중복 가능성을 표시하고 부원 담당자가 확인한다.
4. 계정과 부원 기록을 연결한 뒤 이번 학기 활동 자격을 부여한다.
5. 신규 가입자는 가입 신청 → 검토 → 승인 → 학기 활동 등록 과정을 거친다.

이름만 같다는 이유로 기존 부원 기록을 자동 연결하지 않는다. 학번 사용 여부는 학교·운영 필요에 따라 결정하며, 학번이나 휴대전화번호를 문서 ID·공개 URL로 사용하지 않는다.

### 4.3 로그인 방식 [결정 필요 D-07]

로그인 제공자는 아직 선택하지 않는다. 다음 기준으로 한 가지 방식부터 고른다.

- 부원 대부분이 이미 사용하는 계정인가?
- 학교 계정만 허용할 것인가?
- 카카오톡 내부 브라우저에서 원래 행사로 돌아올 수 있는가?
- 계정을 잃거나 바꿨을 때 부원 기록을 안전하게 이어갈 수 있는가?
- 유지 비용과 차기 임원의 운영 부담은 감당 가능한가?

로그인 후 원래 열었던 행사 상세로 돌아온다. 부원 승인 대기 상태에는 승인 진행 안내와 문의 경로를 보여준다.

## 5. 부원·가입·학기 관리

### 5.1 서로 분리할 정보

| 구분 | 설명 | 예시 상태 |
|---|---|---|
| 계정 | 로그인 수단 | 사용 가능, 이용 제한 |
| 부원 | 동아리 안에서 한 사람의 지속적인 기록 | 재적, 탈퇴 |
| 학기 활동 | 특정 학기의 활동 자격 | 등록 대기, 활동, 휴동, 종료 |
| 가입 신청 | 신규 지원과 심사 | 제출, 검토 중, 승인, 미승인, 철회 |
| 회비 납부 | 해당 학기의 납부 의무와 기록 | 납부 대상, 확인 대기, 완료, 면제 |
| 임원 배정 | 역할과 기간 | 시작일, 종료일, 담당 범위 |

회비 미납 때문에 부원 기록을 삭제하지 않는다. 이전 학기 참가 기록도 새 학기 생성 시 초기화하지 않는다.

### 5.2 명부 기본 항목 [기본안]

- 내부 부원 ID, 표시 이름, 가입 기수 또는 가입일.
- 학교·학과·학번: 각각 실제 필요한지 결정 후 수집.
- 연락 수단: 행사 운영에 필요한 연락처 1개를 우선 검토.
- 이번 학기 활동 상태, 가입 승인 상태.
- 역할·담당 범위·임기.
- 생성·수정 시각과 담당자.
- 본인의 정보 수정 요청 및 처리 상태.

음주량, 주민등록번호, 신분증 사본, 불필요한 건강정보는 기본 명부에 넣지 않는다. 활동 선호도는 선택 응답으로 분리한다.

### 5.3 기존 약 100명 등록

1. 명부 원본의 보유자와 최신 기준일을 정한다.
2. 필요한 열만 추린 가져오기 양식을 만든다.
3. 중복·빈 값·형식 오류를 미리 보여준다.
4. 임원이 수정한 뒤 등록 대상과 건수를 확인한다.
5. 실제 데이터 반영은 별도로 승인된 절차에서 수행한다.
6. 부원에게 본인 연결과 정보 확인을 안내한다.

기존 원본은 이 기획서에 첨부하지 않는다. 사용자 이름·연락처 등 실제 개인정보를 개발 예제 데이터로 사용하지 않는다.

### 5.4 가입과 재등록 정책

- 신규 모집은 모집 기간, 대상, 회비, 활동 안내, 문의를 갖춘 별도 안내로 제공한다.
- 모집 종료 시 신청 버튼 대신 다음 모집 안내를 보여준다.
- 가입 신청과 행사 신청은 구분한다.
- 새 학기에는 이전 부원을 복제하지 않고 학기별 활동 기록을 추가한다.
- 활동 상태 변경 사유는 필요한 범위에서만 기록하고 자유로운 평판 메모는 기본 기능에 넣지 않는다.
- 졸업생·휴학생·외부인 참여는 별도 대상 유형으로 검토한다. **[결정 필요 D-08~D-11]**

## 6. 행사와 교육 운영

### 6.1 모든 활동이 공유하는 행사 항목

| 묶음 | 필드 |
|---|---|
| 기본 | 제목, 유형, 한 줄 소개, 상세 설명, 대표 이미지 |
| 일정 | 시작·종료, 신청 시작·마감, 취소 마감 |
| 장소 | 장소명, 위치 안내, 집합 안내, 공개 범위 |
| 참가 조건 | 신청 대상, 정원, 대기 허용, 신청 방식 |
| 비용 | 무료 여부, 참가비, 납부 기한, 환불 규칙 |
| 준비 | 담당자, 도우미, 준비물, 재료 목록, 준비 체크리스트 |
| 신청 질문 | 필수·선택 질문, 응답 공개 범위 |
| 후속 작업 | 출석, 정산, 재고 반영, 후기, 결과 기록 |
| 게시 | 초안·게시 여부, 공개/부원 전용 노출 범위 |

행사 유형은 분류이다. 교육·총회·모임별로 질문과 기본값을 저장하는 템플릿을 두되 행사마다 수정할 수 있다.

### 6.2 행사 생애주기

~~~mermaid
flowchart LR
    A[초안] --> B[게시·신청 대기]
    B --> C[모집 중]
    C --> D[모집 마감]
    D --> E[진행 완료]
    E --> F[정산·재고 확인]
    F --> G[운영 종료]
    B --> X[행사 취소]
    C --> X
    D --> X
~~~

- 정원 마감과 신청 기간 마감은 화면에서 구분한다.
- 게시 취소·행사 취소·참가자 개인 취소는 별개의 상태이다.
- 행사 취소 시 신청자 안내와 환불 대상 확인 작업을 생성한다.
- 행사 취소 자체가 실제 환불 완료를 의미하지 않는다.
- 운영 종료 후 수정은 담당 권한과 사유를 요구하고 변경 이력을 남긴다.

### 6.3 참가 신청 기본 정책 [기본안]

- 대상: 이번 학기 활동 부원. 예외 대상은 행사별로 명시한다.
- 방식: 선착순, 사용자당 동일 행사 유효 신청 1건.
- 유료 행사: 자리가 있으면 납부 대기로 등록하고 그 자리를 정원에 포함한다.
- 무료 행사: 자리가 있으면 참가 확정으로 등록한다.
- 대기 신청자는 정원에 포함하지 않는다.
- 신청 순서와 마감 판단은 서버 시각을 기준으로 한다.
- 중복 클릭·네트워크 재시도는 같은 신청으로 처리한다.
- 기본 질문은 행사별 추가 질문 0~3개로 시작한다.
- 정원보다 확정·납부 대기 인원이 많은 값으로 정원을 줄이지 못하게 한다.
- 이미 신청자가 있는 행사에서 장소·시간·참가비·정책을 바꾸면 영향 대상과 안내 작업을 보여준다. 참가비 변경을 기존 청구에 조용히 덮어쓰지 않는다.

### 6.4 신청·납부·출석은 별도 상태로 관리

| 종류 | 상태 예시 |
|---|---|
| 신청 | 대기, 참가 등록, 취소, 만료 |
| 납부 | 해당 없음, 미납, 확인 요청, 납부 완료, 환불 대기, 부분 환불, 환불 완료 |
| 출석 | 미확인, 출석, 불참, 불참 사유 확인 |
| 화면에 보이는 요약 | 대기 3번, 납부 대기, 참가 확정, 신청 취소 등 |

유료 행사의 화면상 참가 확정은 참가 등록과 납부 완료를 함께 확인한다. 임원은 각 상태를 따로 확인하며 한 번의 변경이 다른 상태를 잘못 덮어쓰지 않아야 한다.

### 6.5 취소·대기·노쇼

- 취소 마감 전에는 본인이 취소할 수 있다.
- 납부 완료 신청을 취소하면 환불 규칙에 따라 환불 검토 대상으로 이동한다.
- 취소 마감 후에는 문의/취소 요청을 받고 임원이 사유와 처리 결과를 남긴다.
- **초기 대기 운영:** 임원이 순서대로 승급 처리하고 직접 연락한다. 아직 수락하지 않은 다음 사람의 자리를 임의로 확정하지 않는다.
- 승급 제안의 응답 기한과 납부 기한을 정하고, 수락한 경우에만 참가 등록한다. 제안 중인 자리는 예약 좌석으로 집계한다.
- 대기 승급 중 신규 신청이 빈자리를 가로채지 못하도록 좌석 예약을 일관되게 처리한다.
- **확장:** 알림과 예약 만료 처리가 검증되면 자동 승급 제안을 도입한다.
- 노쇼는 담당자 확인 이후 기록한다. 자동 벌금·자동 제명은 기본안에 포함하지 않는다.

취소 시점, 환불 기준, 대기 응답 시간, 노쇼 대응은 실제 운영 전에 결정한다. **[결정 필요 D-12~D-16]**

### 6.6 교육 운영의 추가 정보

- 교육 수준, 학습 목표, 회차, 진행자, 예상 시간.
- 사용하는 도구, 실습 레시피, 준비 재료, 자료.
- 첫 버전에서는 회차 하나를 독립 행사 하나로 운영한다.
- 시리즈 묶음 수강, 선수 교육, 수료 기준은 확장 기능으로 둔다.
- 단순 출석과 교육 수료를 같은 의미로 사용하지 않는다.
- 재료 대체·논알코올 선택이 운영에 필요한 경우 최소한의 선택 질문으로 받는다. 의학적 진단이나 상세 병력을 요구하지 않는다.

### 6.7 행사 준비·마무리 체크리스트 [기본안]

- 준비: 담당자 지정 → 장소 확인 → 정원·예산 결정 → 재료 확인 → 신청 열기.
- 전날: 참가·대기·미납 확인 → 공지 → 도구·재료 준비 → 현장 역할 배정.
- 당일: 출석 → 추가 안내 → 사용 재료 메모 → 정리.
- 종료 후: 실제 지출·환불 확인 → 재고 사용 반영 → 익명 만족도 선택 수집 → 개선점 기록.
- 모든 후속 작업이 완료되거나 남은 사유가 기록되면 운영 종료로 처리한다.

## 7. 회비·참가비·지출·정산

### 7.1 구분

| 항목 | 의미 | 연결 대상 |
|---|---|---|
| 학기 회비 | 해당 학기 활동을 위한 회비 | 부원 + 학기 |
| 행사 참가비 | 특정 행사 참가 비용 | 신청 |
| 공용 지출 | 공용 도구·소모품 등 | 학기 또는 운영 항목 |
| 행사 지출 | 재료·장소 등 행사 비용 | 행사 |
| 환불 | 납부 건의 일부·전체 반환 | 원래 납부 건 |

### 7.2 첫 버전 처리 [기본안]

- 계좌이체 후 재무 담당자가 실제 확인하고 납부 상태를 바꾼다.
- 부원의 '입금했어요' 클릭은 확인 요청이다. 납부 완료로 자동 바뀌지 않는다.
- 납부액·확인 시각·확인자·연결 대상·필요한 메모를 저장한다.
- 중복 입금·부분 납부·과오납·환불을 예외 처리 대상으로 분리한다.
- 금액은 원 단위 정수로 관리한다.
- 영수증 이미지에는 불필요한 개인 정보가 포함되지 않도록 업로드 안내를 둔다.
- 실제 송금·환불·은행 거래 조회는 시스템 밖에서 수행하고 확인 결과만 기록한다.
- 정산 수정은 원기록을 지우는 대신 정정 이력을 남긴다.

### 7.3 행사 결산

- 예상 수입 / 실제 수입 / 실제 환불 / 행사 지출을 분리한다.
- 미납금은 실제 수입에 포함하지 않는다.
- 재고 구매 지출과 그 재고의 행사 소모 추정 비용을 합쳐 이중 비용으로 표시하지 않는다.
- 현금 기준 결산과 재료 소모 추정치는 서로 다른 지표로 표시한다.
- 회비·환불·영수증 보존 정책, 계좌 안내 공개 범위는 결정 전이다. **[결정 필요 D-17~D-20]**

## 8. 재고·도구·구매 관리

### 8.1 관리 대상

| 분류 | 예시 | 기본 관리 단위 |
|---|---|---|
| 주류 | 진, 럼, 리큐르 등 | 미개봉 병 + 개봉 잔량 |
| 비주류 재료 | 주스, 시럽, 탄산수 등 | 품목별 병·mL·개 |
| 신선 재료 | 과일, 허브 등 | 개·g 등 선택 |
| 소모품 | 컵, 빨대, 냅킨 등 | 개·팩 |
| 도구·비품 | 셰이커, 지거, 글라스 등 | 개·상태·위치 |

### 8.2 품목 정보

- 품목명, 분류, 규격, 기본 단위, 사진.
- 보관 위치, 최소 보유 기준, 사용 가능 여부.
- 현재 잔량, 마지막 확인일, 확인자.
- 구매 단가와 구매일은 필요한 경우 기록한다.
- 소비기한·개봉일은 해당되는 품목에만 적용한다.
- 병 규격이 다르면 별도 품목/규격으로 구분한다.
- 도구는 소모량 대신 사용 가능·파손·수리·분실 상태를 관리한다.

### 8.3 술 잔량 모델 [기본안]

첫 운영은 **간편 잔량 기록**을 채택하는 안이다.

- 미개봉: 정수 병 수.
- 개봉: 병별 식별자와 대략적인 잔량 100% / 75% / 50% / 25% / 0%.
- 병 규격을 이용해 예상 mL를 계산할 수 있으나 '추정' 표시를 붙인다.
- 예: 700mL 규격 미개봉 2병 + 개봉 A 50% + 개봉 B 25% → 추정 1,925mL.
- 같은 품목의 여러 개봉 병을 한 병처럼 합치지 않는다.
- 개봉은 미개봉 1병을 개봉 병 1개로 옮기는 상태 변경이며 총량 증가가 아니다.
- 남은 재료의 실제 계량이 필요해지면 mL 직접 기록 방식을 도입한다.
- 추정 잔량과 정밀 계량이 섞이면 기록 방법과 마지막 실사 시각을 함께 표시한다.

### 8.4 재고 변경은 사유가 있는 기록으로 남긴다

| 종류 | 의미 | 필요한 정보 |
|---|---|---|
| 초기 실사 | 시작 재고 등록 | 기준일·수량·기록자 |
| 구매 입고 | 새로 들어온 재료 | 품목·규격·수량·위치·구매 연결 |
| 행사 사용 | 행사에서 사용 | 행사·실제 사용량 또는 사용 후 잔량 |
| 폐기 | 사용 불가 재료 제거 | 수량·사유 |
| 위치 이동 | 보관 장소 변경 | 출발·도착 위치 |
| 실사 조정 | 기록과 실제 차이 보정 | 이전 값·확인 값·차이·사유 |
| 정정 | 잘못 입력한 기록 수정 | 원기록 참조·정정 이유 |

- 현재 재고 숫자만 덮어쓰는 방식으로 끝내지 않는다.
- 음수 재고를 기본적으로 허용하지 않는다.
- 동시에 수정하면 최신 값과 차이를 보여주고 충돌을 해결한다.
- 같은 행사 정산을 재실행해도 중복 차감되지 않아야 한다.
- 위치 이동은 전체 보유량을 바꾸지 않는다.
- 실사 이후 과거 사용 기록을 입력하면 기준 시각을 확인해 중복 차감을 막는다.

### 8.5 행사 준비와 연결

**준비 단계:** 필요한 재료 목록과 예상 소모량을 작성한다. 예상량은 실제 재고를 차감하지 않는다.

**현장 단계:** 필요한 물품을 가져가고 사용량 또는 사용 후 잔량을 기록한다.

**마무리 단계:** 재고 담당자가 실제 사용 기록을 확인해 반영한다.

**[확장]** 레시피 × 예상 잔 수로 예상 소모량을 계산하고 재고를 예약한다. 이때 보유량·예약량·사용 가능량을 분리한다. 레시피상 수량이 실제 사용량과 같다고 가정하지 않는다.

### 8.6 구매와 도구 대여

- 초기 구매: 부족 품목 목록 → 담당자 확인 → 외부에서 구매 → 입고 기록.
- 시스템에서 자동 주문하거나 결제하지 않는다.
- **[확장]** 구매 요청·예산 승인·구매 완료·입고 완료의 상태 관리.
- **[확장]** 도구 대여자·반납 예정일·반납 상태·파손 기록.
- 재고 실사 주기와 기록 책임자를 먼저 정한다. **[결정 필요 D-21~D-24]**

## 9. 공지·자료·사진·소통

### 9.1 공지

- 공개 / 부원 전용 / 임원 전용을 구분한다.
- 제목, 본문, 첨부, 대상, 게시 기간, 중요 여부, 담당자를 저장한다.
- 첫 버전은 공지 게시와 행사 링크 복사를 제공한다.
- 카카오톡 공지 전송은 임원이 직접 수행한다.
- 공개 링크를 알아도 부원 전용 본문과 첨부는 권한 확인 후 제공한다.
- 시간·장소 변경 공지는 기존 설명 수정과 별도로 변경 내용을 남긴다.

### 9.2 자료실·레시피 [확장]

- 자료 유형: 교육 자료, 레시피, 운영 매뉴얼, 회의록.
- 레시피: 이름, 재료·수량, 기법, 잔, 제작 단계, 대체 재료, 작성자, 공개 범위.
- 임원 회의록과 부원 교육 자료의 공개 범위를 구분한다.
- 자료와 이미지의 사용 권한을 확인하고 출처를 남길 수 있게 한다.
- 레시피 등록을 재고 품목 등록의 필수 조건으로 만들지 않는다.

### 9.3 사진과 후기

- 공개 홈페이지 게시용 사진은 대상자의 동의·게시 가능 범위를 확인한다.
- 신청 필수 동의와 사진 공개 선택 동의를 분리한다.
- 첫 버전에는 임원이 선별한 활동 기록만 게시한다.
- **[확장]** 부원 후기 제출 → 검토 → 게시, 신고·숨김 처리.
- 실명 후기나 사진 공개가 행사 참여의 필수 조건이 되지 않도록 한다.

### 9.4 의견 수렴

- 첫 운영 전에 활동 선호, 가능한 요일, 교육 경험을 묻는 짧은 설문을 제안한다.
- 만족도 조사는 응답 여부와 공개 범위를 알리고 개인 평가 자료로 남용하지 않는다.
- **[확장]** 임원 선출·안건 투표는 익명성, 투표 자격, 중복 방지, 집계 검증을 따로 기획한다.
- 문의·고충 접수는 담당자와 확인 주기를 정한 뒤 공개한다. **[결정 필요 D-25~D-27]**

## 10. 임원 업무와 인수인계

### 10.1 운영실 첫 화면은 할 일을 보여준다

- 오늘 진행하는 행사와 출석 바로가기.
- 승인 대기 부원.
- 납부 확인 요청과 환불 대기.
- 마감 임박 행사, 대기 승급 확인.
- 부족 재고와 실사 미확인 품목.
- 종료 후 정산·재고 정리가 남은 행사.

보이는 항목은 담당 권한에 따라 달라진다. 재고 담당자의 첫 화면에 모든 부원의 미납 정보를 노출하지 않는다.

### 10.2 학기 운영 기록

- 학기 기본 정보, 운영 책임자, 임원 역할.
- 행사별 준비 체크리스트와 개선점.
- 학기 수입·지출 요약과 재고 실사 결과.
- 다음 학기에 반복할 행사 템플릿.
- 운영 정책 변경 기록.
- 미해결 환불·반납·문의 목록.

### 10.3 인수인계 절차 [기본안]

1. 다음 임원 개인 계정을 확인한다.
2. 필요한 역할과 임기만 배정한다.
3. 운영 매뉴얼과 미완료 업무를 함께 확인한다.
4. 이전 임원의 권한 종료를 확인한다.
5. 계정·도메인·서비스의 운영 책임과 복구 연락망을 별도로 점검한다.
6. 비밀번호나 비밀 키를 기획서·회의록에 복사하지 않는다.

## 14. 시각 디자인·모바일·접근성

### 14.1 브랜드 방향 [기본안]

- 분위기: 칵테일 바의 정돈된 인상과 대학 동아리의 친근함.
- 색상 후보: 짙은 녹색, 크림색, 검정에 가까운 본문색, 라임 계열 강조색.
- 공개 홈페이지는 사진과 여백으로 활동 분위기를 전달한다.
- 라운지·운영실은 밝은 배경과 높은 가독성을 우선한다.
- 기존 로고와 사진이 다시 제공되면 사용 가능 여부를 확인하고 적용한다.
- 텍스트 로고만으로도 첫 버전을 시작할 수 있다.
- 실제 개최하지 않은 활동을 과거 실적으로 꾸미지 않는다.
- 다크 모드와 복잡한 애니메이션은 초기 범위에서 제외한다.

**[결정 필요 D-29, D-30]**

### 14.2 모바일 원칙

- 모바일 핵심 흐름은 가로 스크롤 없이 사용할 수 있게 한다.
- 주요 버튼 높이는 44~48 CSS px를 자체 설계 목표로 둔다. 이는 이 프로젝트의 제안값이다.
- 하단 고정 버튼이 키보드·브라우저 UI·본문을 가리지 않도록 한다.
- 긴 표는 카드 요약으로 바꾸고 상세를 펼쳐서 본다.
- 날짜·금액·상태를 사진보다 먼저 확인할 수 있는 행사 카드를 사용한다.
- 날짜 입력만 요구하기보다 일정 선택을 돕되 키보드 입력도 가능하게 한다.
- 임원용 대량 편집은 PC에 적합하게 설계하되 모바일에서도 개별 조회·수정은 가능하게 한다.
- 화면 크기 360·390·768·1280 CSS px를 검토 기준으로 삼고 실제 기기로 확인한다.

### 14.3 접근성과 입력

- 입력 필드에 보이는 라벨과 필수·선택 표시를 제공한다.
- 색상만으로 납부·출석·오류 상태를 구별하지 않는다.
- 키보드 이동, 초점 표시, 버튼 이름, 오류 메시지 연결을 확인한다.
- 오류 발생 시 어떤 항목을 어떻게 수정해야 하는지 안내한다.
- 긴 폼은 논리적인 단계로 나누고 진행 상태와 이전 단계 복귀를 제공한다. 짧은 신청은 한 화면으로 끝낸다. [W3C 다단계 폼 지침](https://www.w3.org/WAI/tutorials/forms/multi-page/)
- 버튼과 링크의 크기·간격을 확인한다. WCAG 2.2의 최소 타깃 크기 기준에는 24×24 CSS px 및 예외 조건이 있으므로 단순 버튼 높이만으로 준수를 단정하지 않는다. [W3C 타깃 크기 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- 사진의 대체 설명과 읽기 순서를 제공한다.
- 카카오톡 내부 브라우저, 모바일 Safari·Chrome에서 로그인 복귀와 신청 완료를 확인한다.
- 접근성 준수 여부는 실제 구현 이후 검증한다.

### 15.3 데이터 일관성 규칙

- 같은 계정에 서로 다른 부원 기록을 임의로 중복 연결하지 않는다. 계정 변경은 확인 절차를 거친다.
- 행사+부원의 신청은 취소 후 재신청해도 이전 이력을 보존한다.
- 좌석 수에는 참가 등록과 아직 유효한 승급 예약만 포함한다.
- 좌석 할당·신청 생성·집계 갱신은 하나의 일관된 처리로 수행한다.
- 환불 합계가 실제 납부 합계를 넘지 않게 검사한다.
- 재고 이동은 출발 차감과 도착 증가가 함께 처리된다.
- 예산·예상 소모량과 실제 지출·재고 변동은 구분한다.
- 시간은 일관된 기준으로 저장하고 화면에는 Asia/Seoul 기준으로 표시한다.
- 금액·수량에 유효하지 않은 문자·음수·허용 범위 초과 값이 들어가지 않도록 한다.
- 화면에서 검사를 우회해도 서버/데이터 계층에서 같은 업무 규칙을 검사한다.
- 집계가 잘못되면 먼저 원인과 차이를 조회하는 보고서를 만든다. 운영 데이터 자동 보정은 별도 승인 없이 수행하지 않는다.

### 16.2 최소 수집·공개 범위

- 기본 명부에는 운영에 실제 필요한 항목만 포함한다.
- 식이·재료 대체 요청은 행사별 필요에 따라 최소 수집하고 열람 담당자를 제한한다.
- 신청자 명단을 일반 공개하지 않는다. 공개 정원 표시는 개인 정보 없는 집계로 제공한다.
- 사진 공개, 선택 설문, 행사 신청 필수 확인을 별도로 구분한다.
- 개인정보 안내에는 수집 목적·항목·이용 범위·보존 기간·문의 경로를 구체화한다.
- 데이터 내보내기는 권한을 제한하고 담당자·시각·대상 범위·사유를 기록한다.
- 명단 파일은 행사 종료 후 처리 지침을 두고 공개 링크로 공유하지 않는다.
- 테스트 데이터와 화면 예시는 가상의 부원만 사용한다.

### 16.3 구현 시 기본 보호

- 메뉴 숨김 외에 서버와 저장소 접근에서도 권한을 검사한다.
- 파일·사진·영수증 첨부에도 원문과 같은 권한 정책을 적용한다.
- 신청·변경 요청은 허용 필드, 형식, 길이, 자격, 마감, 정원, 중복 여부를 검사한다.
- 임원 권한·정산·재고 조정의 변경 이력을 남기되 로그에 비밀 값이나 불필요한 개인정보를 기록하지 않는다.
- 인증 정보를 기획서·저장소·브라우저 코드·화면 출력에 넣지 않는다.
- 로그인 제한·관리자 보호·계정 복구 방법은 선택한 인증 제공자에 맞춰 검토한다.
- 자동 요청 남용 방지와 호출량 보호를 계획하되 기술 제품은 지금 확정하지 않는다.
- 백업과 복구는 파일 존재 확인에 그치지 않고 분리된 환경에서 복구 검증을 한다.

### 16.4 개발·운영 변경 경계

- 기능 브랜치에서 작업하고 구현에 맞는 검증을 수행한다.
- 실제 비밀 값은 사용하지 않고 필요한 변수명과 안전한 예시만 문서화한다.
- 인증·권한·비밀 정보·운영 설정 변경은 영향과 검증 결과를 먼저 정리한다.
- 운영 배포, 운영 데이터 변경·삭제, 마이그레이션, 실제 권한·키·과금·도메인 변경은 해당 작업에 대한 명시적 승인 범위를 확인한다.
- 기획서에 '자동 처리'라고 적힌 기능은 해당 운영 작업을 지금 실행하라는 승인이 아니다.
- Firebase 등 특정 제품은 미선정이다. 제품 선택 후 해당 권한 규칙과 배포 절차를 작성한다.

| 재고 기록 누락 | 현장 실사 → 차이 보고 → 승인된 담당자가 사유와 함께 조정 |
| 개인정보가 잘못 공개됨 | 접근 제한·범위 확인·담당자 보고 후 필요한 후속 조치 |
| 담당 임원 장기 부재 | 대체 담당자 배정과 미처리 업무 인계 |

안전·현장 대응 담당자, 학교 규정, 주류 제공 자격 확인 방법은 서비스 정책과 함께 정한다. 구체 법률 판단이나 사고 대응 전문 지침은 이 초안에서 확정하지 않는다.

## 17. 기술·비용·유지관리 방향

### 17.1 기술 선택 전에 고정할 설계

- 하나의 웹앱 안에 공개·라운지·운영실 모듈을 둔다.
- 공통 로그인, 역할 검사, 행사·부원·재고 데이터를 사용한다.
- 공개 콘텐츠는 검색과 공유에 필요한 제목·설명·이미지를 제공한다.
- 부원·임원 전용 정보는 검색엔진 제외 설정뿐 아니라 실제 인증·권한으로 보호한다.
- 정원·납부·재고 같은 핵심 변경을 신뢰할 수 있는 데이터 처리 계층에서 수행한다.
- 운영자가 바뀌어도 자료를 내보내고 운영 계정을 인수인계할 수 있게 한다.
- 첫 버전은 반응형 웹으로 시작한다. 홈 화면 설치·오프라인 기능은 별도 검토한다.

### 18.3 첫 시범 운영 시나리오

**시나리오 A: 개강총회**

- 무료 행사, 전체 활동 부원 대상.
- 장소 수용 인원을 확인해 정원 설정.
- 참가 신청과 취소, 현장 출석 확인.
- 총회 안내 공지와 끝난 뒤 결과 기록.

**시나리오 B: 입문 교육**

- 예시 정원 20명, 유료 여부와 금액은 별도 결정.
- 신청 → 납부 확인 → 수동 대기 승급 → 출석.
- 재료 준비 → 사용 후 잔량 입력 → 지출·환불 확인.
- 두 시나리오를 같은 행사 기능으로 운영할 수 있어야 한다.

### 18.4 일정 산정 방식

지금은 개발자 수·작업 시간·기술·운영 시작일이 미정이므로 확정 주차를 약속하지 않는다.

1. 핵심 결정을 반영한 기획서 0.2 작성.
2. 7개 핵심 화면의 클릭 가능한 시안 검토.
3. 1A 기능 묶음별 개발량 산정과 일정 확정.
4. 소수 부원 시험 → 첫 행사 시범.
5. 1B 완성과 재고 실사·통합 운영.
6. 반복 행사 후 확장 우선순위 재평가.

## 21. 사용자가 결정하거나 제안할 사안

**이 표의 마지막 열에 답을 적으면 된다.** '기본안 채택', '수정: …', '보류' 형식이면 충분하다. 제안값을 적어둔 것은 합의가 완료되었다는 뜻이 아니다.

- **착수 전 필수:** 데이터·권한·핵심 흐름을 바꾸므로 구현 전에 결정.
- **첫 운영 전:** 개발 중 확정 가능하지만 실제 부원 사용 전에 필요.
- **후속:** 해당 확장 기능을 만들 때 결정.

## 22. 사용자가 준비하면 좋은 자료

현재 없는 자료는 새로 만들어야 하는 의무가 아니라 다음 기획을 구체화하기 위한 준비 후보이다.

| 자료 | 필요한 이유 | 없을 때 진행안 |
|---|---|---|
| 동아리 한 줄 소개·활동 목표 | 홈페이지 핵심 문구 | 2장의 소개 후보 검토 |
| 임원 명단과 담당 업무 | 권한·업무 배정 | 개인 이름 없이 역할부터 합의 |
| 기존 부원 명부의 열 이름·기준일 | 초기 가져오기 설계 | 빈 양식부터 만들고 담당자 확인 |
| 학기 일정·장소 사용 조건 | 행사 정원·시간 결정 | 가상 일정으로 화면만 검토 |
| 회비·참가비·환불 운영 의견 | 신청·납부 흐름 | 무료 시범 행사부터 검토 |
| 주류·재료·도구 목록과 규격 | 재고 분류·단위 | 대표 품목 10개로 기록 방식 시험 |
| 실제 보관 위치 | 재고 탐색·이동 | 위치 이름부터 정리 |
| 로고·활동 사진·사용 가능 여부 | 공개 디자인 | 텍스트 중심 초안 |
| 기존 공지·신청 질문 예시 | 반복 입력 최소화 | 행사별 질문 0~3개 기본안 |
